# Finding catalogue

Every finding the detectors in [`tools/checks.mjs`](../tools/checks.mjs) can
report: 32 of them, across 11 checks.

This file is generated by `node tools/gen-catalogue.mjs` from
[`tools/findings.mjs`](../tools/findings.mjs) and
[`tools/limits.mjs`](../tools/limits.mjs). Edit those, not the tables. CI
regenerates it and fails if the result differs, so the prose here cannot
drift away from the code it describes.

A check is not a finding, and the distinction is the reason this file
exists. Eleven checks reported findings labelled with the check id alone,
and the eleven example pairs reached 17 of the 32 reasons below.
The rest had never been observed firing. Writing the fixtures that reach
them turned up nine defects in the detectors, seven of which were in
branches no pair touched.

The third column is the one to read. Each finding says what it cannot
establish, because the fix column is worthless without it: a finding is a
shape in a file, not a measurement of what a visitor experiences.

Every finding here is observed firing on a real page in CI. The last
column says where, and `test/catalogue.mjs` asserts that set against this
catalogue in both directions, so a finding cannot sit here having never
fired and a detector cannot emit one nothing describes.

## Interactive control with no accessible name

`unnamed-control`, WCAG 1.1.1, WCAG 4.1.2.

The markup supplies nothing for this control to be announced as: no text content, no image alt, no aria-label and no aria-labelledby that resolves inside the file.

| Finding | Fix | What it cannot say | Observed in |
|---|---|---|---|
| **`aria-hidden-content-only`**<br>Everything inside the control carries aria-hidden="true", so the glyph is correctly withheld and nothing is left to announce. | Add visually hidden text inside the control. It survives translation, a failed icon request and voice control, none of which an aria-label does as well. | That a user hears nothing. A theme script can set aria-label on load, and this reads the file before any script has run. | `examples/unnamed-icon-button` |
| **`svg-without-title`**<br>The only content is an inline graphic with no title element, no aria-label and no aria-hidden, so it is exposed and anonymous at once. | Decide which it is. A decorative icon takes aria-hidden="true" plus visually hidden text on the control; a meaningful one takes a title element inside the svg. | Which of the two it is. That is a judgement about what the icon means on this page. | `test/fixtures/labelling-variants.html` |
| **`image-without-alt`**<br>The only content is an image whose alt is absent or empty, which is the shape a merchant produces when the theme has no icon for what they wanted. | Put the name on the image with alt, not on the control. An image inside a link is named by its alt, and that is the one place a merchant can reach from the admin. | Whether an empty alt was deliberate. On a decorative image it is correct, and then the control needs its own name instead. | `test/fixtures/labelling-variants.html` |
| **`dangling-labelledby`**<br>aria-labelledby names an id that nothing in the file has, which is what happens when a section is copied and the element it referred to stays behind. | Point it at an id that exists, or delete the attribute and name the control directly. A dangling reference is treated as no name at all, not as a fallback. | That the id is missing at runtime. A different section can render it, and on a storefront assembled from sections that is worth checking before editing. | `test/fixtures/labelling-variants.html` |
| **`empty-labelledby-target`**<br>aria-labelledby resolves to an element that is present and holds no text, which is what a metafield or a block setting does when it is empty for this product. | Give the referenced element a fallback in Liquid, or name the control directly. An empty target is worse than a dangling one, because it passes a check that only looks for the id. | Whether it is empty for every product. One product with a populated metafield is enough to hide this. | `test/fixtures/labelling-variants.html` |
| **`empty-label`**<br>aria-label is present and empty once trimmed, which is a theme setting the merchant left blank. | Supply a default in the Liquid that renders the attribute, so a blank setting falls back to wording rather than to nothing. | Nothing beyond the file. This one is unambiguous: an empty aria-label is an empty name. | `test/fixtures/labelling-variants.html` |
| **`no-labelling-at-all`**<br>No text, no image alt, no aria-label and no aria-labelledby. Often a control whose glyph was in a pseudo-element on a class the theme no longer sets. | Add the name as text. If the control is genuinely redundant, remove it from the tab order rather than naming it, because an empty control in the tab order is a stop with nothing to say. | Whether a name arrives from generated content. A label supplied by ::before is one this cannot read and a screen reader may or may not announce. | `test/fixtures/labelling-variants.html` |

## An interactive element inside another interactive element

`nested-interactive`, WCAG 4.1.2.

One target carries two conflicting roles. Screen readers disagree about what to announce, keyboard activation is unpredictable, and the inner control may be unreachable.

| Finding | Fix | What it cannot say | Observed in |
|---|---|---|---|
| **`control-in-link`**<br>A control inside the anchor that wraps a whole product card, which is the common shape of this defect on a storefront. | Make them siblings and stretch a pseudo-element from the title link across the card, so the card stays clickable for a pointer without nesting. | How badly it behaves, which varies by pairing and by screen reader. | `examples/nested-interactive-card` |
| **`link-in-link`**<br>A link inside a link, usually a badge that became a link to a collection while sitting inside the card anchor. | Unlink the badge. A sale badge is a label, and the card already links to the product. | Which of the two links a user meant to activate, which is the point: neither can the browser. | `test/fixtures/card-nested-controls.html` |
| **`control-in-control`**<br>Two controls nested where neither is a link, such as a checkbox inside an element given role="button" so the whole thing is clickable. | Keep the native control and style its label, rather than wrapping it in something that claims to be a control itself. | Which role wins. Browsers and screen readers disagree, and that disagreement is the defect. | `test/fixtures/card-nested-controls.html` |

## Variant swatch built from a non-interactive element

`swatch-not-a-control`, WCAG 1.3.1, WCAG 2.1.1, WCAG 4.1.2.

An element carrying an option value is neither focusable nor announced as a control, so the option cannot be chosen from a keyboard and has no role, name or state.

| Finding | Fix | What it cannot say | Observed in |
|---|---|---|---|
| **`option-data-attribute`**<br>A div or span carrying the option value in a data attribute, with no role, no tabindex and no name. | A fieldset and legend around native radio inputs, with the colour name as text rather than as a border colour. | That the swatch does nothing on click. It almost certainly works with a mouse, which is why it survives testing. | `examples/swatch-not-a-control` |
| **`class-hook-only`**<br>The same defect in a theme that reads the option out of the element text, so there is no data attribute to find it by, only a class. | The same fix. Note that the class is the only hook here, so a theme that renames it puts the swatch beyond this check entirely. | Anything about a theme using a third naming convention. This finding is as good as the class list it matches. | `test/fixtures/swatch-class-hook.html` |

## Skip link that cannot be focused, or whose target cannot take focus

`skip-link-unusable`, WCAG 2.4.1.

Either a rule in this file removes the link from the tab order, or the fragment it points at does not exist, or the target cannot accept focus because it is not natively focusable and has no tabindex.

| Finding | Fix | What it cannot say | Observed in |
|---|---|---|---|
| **`hidden-by-display`**<br>A rule in this file takes the skip link out of the tab order with display: none, which is the version everybody quotes. | Offset it off screen with position and a negative coordinate, and bring it back on focus. display: none means :focus never happens. | That no later rule overrides it. This does not resolve the cascade and reads declarations as written. | `examples/skip-link-unusable` |
| **`hidden-by-visibility`**<br>The same removal written with visibility: hidden, which is just as complete and survives a review that greps for display: none. | The same offset pattern. Reach for it rather than for visibility: visible on focus, which does not restore a child of a hidden ancestor. | That no later rule overrides it, and in this spelling that matters more: visibility is inherited, so a hidden ancestor can produce this without any rule naming the link at all, and no rule naming the link can undo it. | `test/fixtures/skip-link-variants.html` |
| **`target-missing`**<br>The fragment the link points at does not exist in the file. This is the failure that outlives a theme update: visible, focusable, announced correctly, and does nothing. | Point it at the id the layout actually renders, and keep the two together in one snippet so they cannot be renamed separately. | That it is missing at runtime, on a page assembled from sections that another section may render. | `test/fixtures/skip-link-variants.html` |
| **`target-not-focusable`**<br>The target exists and cannot accept focus, because it is not natively focusable and carries no tabindex. | tabindex="-1" on the target. Without it several browsers scroll to it and leave focus behind, so the link appears to work. | Whether focus lands once the attribute is there. That is browser behaviour and the way to know is to press Tab. | `examples/skip-link-unusable` |

## Focus indicator removed by a stylesheet rule

`focus-outline-removed`, WCAG 2.4.7.

A rule in this file sets outline to none or zero on focus, or universally, and no later rule restores an indicator for :focus-visible.

| Finding | Fix | What it cannot say | Observed in |
|---|---|---|---|
| **`universal-reset`**<br>A universal selector removes the outline and nothing anywhere in the document restores an indicator for :focus-visible. | :focus-visible, which shows the indicator for keyboard input and suppresses it for a pointer, which is what the reset was reaching for. | That no indicator is visible. A box-shadow or a border change can be doing the job, and neither is read here. Nor whether an indicator that does exist meets the contrast and thickness 2.4.11 asks for. | `examples/focus-outline-removed` |
| **`focus-reset`**<br>The same removal scoped to named components rather than applied universally, which is what a theme accumulates one component at a time. | The same fix, done once in a baseline rather than per component, because this finding arrives in batches and each addition looked small on its own. | Which component the visitor will reach first. A per component reset leaves the indicator intact on everything it has not reached yet, so a keyboard pass over one page can come back clean. | `test/fixtures/focus-reset-on-focus.html` |

## Viewport meta tag prevents zooming

`viewport-scaling-blocked`, WCAG 1.4.4.

The viewport declaration sets user-scalable=no or a maximum-scale below 2, which is an author instruction not to allow text to be enlarged.

| Finding | Fix | What it cannot say | Observed in |
|---|---|---|---|
| **`user-scalable-no`**<br>The viewport declaration carries user-scalable=no, which is an author instruction not to allow text to be enlarged. | Remove it, and set a 16px minimum font size on fields, which is usually what it was added for. | That a visitor cannot zoom. iOS Safari has ignored this since version 10. Remove it anyway: it still applies in several in-app webviews, and it is free. | `examples/viewport-scaling-blocked` |
| **`maximum-scale-below-2`**<br>maximum-scale is set below 2, so enlargement is capped under the 200 per cent that 1.4.4 asks for. | Remove the cap rather than raising it. There is no value for it that helps. | Anything about the harder half of 1.4.4: fixed pixel heights that clip text once it is enlarged. | `examples/viewport-scaling-blocked` |

## Drawer or modal container without dialog semantics

`dialog-not-a-dialog`, WCAG 1.3.1, WCAG 4.1.2.

A container named as a drawer, modal or dialog is missing role="dialog", aria-modal="true" or an accessible name, so nothing announces what opened or keeps the page behind it out of the way.

| Finding | Fix | What it cannot say | Observed in |
|---|---|---|---|
| **`no-dialog-role`**<br>A container named as a drawer, modal or popup carries no role="dialog", so nothing announces that something opened. | role="dialog" on the container, or the dialog element, which brings the role with it. | Anything at all about behaviour, which is where drawers actually fail. test/gap.mjs asserts that rather than leaving it here. | `examples/dialog-not-a-dialog` |
| **`no-aria-modal`**<br>No aria-modal="true", so nothing tells the accessibility layer that the page behind this is out of the way. | aria-modal="true", and make the background genuinely inert, because the attribute is a claim rather than a mechanism. | Whether the background is inert. The attribute and the behaviour are independent, and this reads only the attribute. | `examples/dialog-not-a-dialog` |
| **`no-accessible-name`**<br>The container has no aria-label and no aria-labelledby, so it opens as an unnamed dialog. | Point aria-labelledby at the heading the drawer already has, rather than duplicating the wording in an aria-label. | Whether the name is useful, only whether there is one. | `examples/dialog-not-a-dialog` |

| Finding | Fix | What it cannot say | Observed in |

## Live region containing text at the moment it enters the document

`live-region-arrives-populated`, WCAG 4.1.3.

The region is in the markup with its message already inside it. There is no mutation for the accessibility layer to observe, so in most screen reader and browser pairs nothing is announced.

| Finding | Fix | What it cannot say | Observed in |
|---|---|---|---|
| **`aria-live-attribute`**<br>A region with aria-live is in the markup with its message already inside it, so there is no mutation for the accessibility layer to observe. | One empty region in the document before the first message, written on a later frame. | That nothing is ever announced. A region that was already in the document and is being re-rendered is a different case this cannot distinguish from first insertion. | `examples/live-region-arrives-populated` |
| **`status-role`**<br>The same defect expressed with role="status", which carries an implicit polite live value. A theme is more likely to use the role, because the Shopify documentation does. | The same fix. The two are separated here because somebody searching their theme will search for one spelling or the other, and finding neither is the usual outcome of searching for the wrong one. | That the role is the whole story. role="alert" is assertive and interrupts, role="status" is polite and waits, and this finding does not judge which of the two the message deserved. | `test/fixtures/status-role-populated.html` |

## Form field with no label, or with a placeholder standing in for one

`field-without-label`, WCAG 1.3.5, WCAG 3.3.2, WCAG 4.1.2.

The field has no label associated by for and id, no wrapping label, no aria-label and no aria-labelledby. Where a placeholder is present, it is the only description of the field and it disappears as soon as the field has content.

| Finding | Fix | What it cannot say | Observed in |
|---|---|---|---|
| **`placeholder-as-label`**<br>The field has no label and a placeholder is the only description of it, which disappears as soon as the field has content. | A real label associated by for and id. Hide it visually if the design needs that, and keep the placeholder only if it adds something the label does not. | That a visually hidden label is enough. It satisfies this finding and still fails the sighted user who wants to check what they typed. | `examples/field-without-label` |
| **`no-label-at-all`**<br>No label and no placeholder either, usually a field whose description is text in a neighbouring element associated with nothing. | Associate the text that is already there, by giving the field an id and the text a for. The wording exists; only the link is missing. | Whether the neighbouring text is the label. That is a judgement about layout. | `test/fixtures/quantity-field-unlabelled.html` |
| **`missing-autocomplete`**<br>A field collecting an email address, telephone number or password with no autocomplete token, which 1.3.5 asks for. | The token for what the field collects. It is also the difference between a form a password manager fills and one it does not. | Anything about name and address fields, which this finding does not cover. | `examples/field-without-label` |

## Control sized below the 24 by 24 CSS pixel minimum

`target-under-24px`, WCAG 2.5.8.

A rule that plainly targets a control fixes both of its dimensions, and at least one of them is under 24 CSS pixels.

| Finding | Fix | What it cannot say | Observed in |
|---|---|---|---|
| **`both-dimensions`**<br>A rule plainly targeting a control fixes both dimensions below 24 CSS pixels, which is what sizing a target to its glyph produces. | A 24 by 24 minimum on the hit area, with the glyph left at its original size. | The rendered size, which padding, line height, a larger child and a pseudo-element all change. It also does not apply the 2.5.8 exceptions for inline links, spacing and user agent sizing. | `examples/target-under-24px` |
| **`one-dimension`**<br>One dimension conforms and the other does not. This is the one that gets missed in review: the target is comfortably wide, somebody checked the width, and 2.5.8 asks for both. | Raise the short axis, usually with padding rather than height so the glyph does not move. Note that the Level AA minimum is 24, not 44: 44 is 2.5.5 at Level AAA. | The rendered size, as above, and in this case the undershoot is often undone by line height on the very element the rule names, which is why the figure here is a declaration and not a measurement. | `test/fixtures/pagination-one-dimension.html` |

## The limits of all of it

These are asserted rather than described. Each one is exercised in
[`test/gap.mjs`](../test/gap.mjs) under its own id, and `tools/verify.mjs`
asserts that the two files name the same set.

A limit marked **both** is the strongest form: the same outcome for a
visitor gets either verdict depending on something that is not a property
of the page, so the finding count carries no information about that
outcome at all.

| Limit | Direction | Bounds | The claim |
|---|---|---|---|
| `cascade-not-resolved` | both | `focus-outline-removed`, `skip-link-unusable`, `target-under-24px` | The checks read the declarations in the file. A document that links a stylesheet is a document whose cascade is partly somewhere else, so the verdict depends on which file a rule happens to live in rather than on what a visitor sees. |
| `declared-size-is-not-rendered-size` | both | `target-under-24px` | A declared width is not a rendered width. Padding, a transform, a larger child and a pseudo-element all change the box, so a conforming declaration can render too small and a small declaration can render large enough. |
| `name-can-change-after-load` | both | `unnamed-control`, `dialog-not-a-dialog`, `field-without-label` | The markup on disk is the markup before any script has run. A name added on load makes a reported finding wrong, and a name removed on load makes an unreported page defective. |
| `semantics-are-not-behaviour` | both | `dialog-not-a-dialog` | Dialog semantics and dialog behaviour are independent. All four combinations of the two verdicts are reachable, so neither predicts the other, and the static verdict carries no information about whether the drawer can be used. |
| `a-name-is-not-a-good-name` | false-negative | `unnamed-control`, `dialog-not-a-dialog` | The checks ask whether there is a name, which is the only half of the question a machine can answer. A control named "click here" satisfies every name check in this repository and fails 2.4.4. |
| `pairs-do-not-cover-the-catalogue` | false-negative | `examples/manifest.json` | The example pairs demonstrate one defect each, so for every check with more than one reason to fire they reach a strict subset of its findings. This repository asserted that every check had a pair, and was green, while fifteen of thirty-two findings had never fired once. The pairs are illustrations; the fixtures are the coverage. |

The long form of the argument, with the parts no assertion reaches, is in
[what the checks do not see](08-what-the-checks-do-not-see.md).
